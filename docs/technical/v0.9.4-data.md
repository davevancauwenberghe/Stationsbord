# v0.9.4 data review

Reviewed 11 October 2026 against the live iRail API and upstream commit
`616ea95b03b7adf72b890a8bdc0e8041cb520e35`.

## Train progress

The vehicle endpoint supplies separate `arrived` and `left` stop flags. Both
main detail views display the last reported station, the next served stop and,
for a board-opened train, the user's selected station. Reported and selected
stops have different labels; departed stops remain visible.

The current V1 converter builds vehicle coordinates from the last visited
station. They must not be displayed as a live GPS position. A current response
with stop flags can report arrival/departure progress. A response without those
flags can only offer a clearly labelled time-based estimate. A stale response,
missing/old timestamp, offline event or failed refresh removes the live marker.
Snapshots older than three minutes are not presented as current reports.
Finishing the timetable alone does not prove that a train has arrived.

Visible live routes refresh once a minute, including an open board dialog.
Background refresh retains a loaded formation for up to fifteen minutes, its
horizontal scroll and selected stop focus. It then
requests the formation again to pick up changes. Manual lookup refresh also requests
the formation. Dated/planned views stay fixed. Replaced/closed views reject late
results. Background formation reuse requires the same train, service date and
language; an unavailable/interrupted formation retains a working retry.

## Dated compositions and overnight services

The current composition controller accepts `date=DDMMYY`. A direct request for
IC1830 on 11 October 2026 returned an M6 formation with an HLE18 at the end;
12 October returned a planned formation with the locomotive at the other end.
These observations verify date support, not ongoing availability or correctness
for every train. Earlier published docs list `data` without `date`.

The proxy validates the actual calendar date, forwards it and isolates its cache
by date. Missing dates are resolved in Europe/Brussels before creating the cache
key. Details request the selected service date, including tomorrow and earlier
service days after midnight; unavailable formations have a normal retry.
A dated formation is indicative and can change before departure.

For today's number lookup before 04:00, when the current-day service starts later
or is not found, there is at most one previous-day lookup. It is selected only
when its expected event range contains now and its terminus has not already
reported arrival/departure. This preserves the date-only search form. The route
summary shows the actual service date; shared custom-date searches retain their
explicit date and do not perform this fallback.

## Carriage orientation

The upstream RIV composition parser derives some orientations from traction
positions and sets the last vehicle to RIGHT. It is not a dependable physical
orientation measurement. Stationsbord's artwork metadata already distinguishes
source filenames from cab-facing direction.

Complete, contiguous AM08/75/80/86/96 and AR41/MW41 sets sharing one positive
material number now orient their two cab drawings outward. The check requires
the expected set length, a cab at each end and only intermediate drawings in
between. Coupled numbered sets are checked independently. It neither reverses
the train nor changes the unit data. Partial, unnumbered, unsupported or
ambiguous sets keep the supplied direction; a missing direction remains an
indicative drawing. I10 VUH/BVUH uses the existing I10 second-class artwork.
No PNG transformations or provenance changes are required.

## Disruptions

Stationsbord still requests and renders explicit train/row/stop alerts when
available. In the reviewed current upstream implementation, the RIV client
collects messages but the V1 vehicle converter returns the vehicle and stops
without converting those messages. An empty response cannot prove that a
service is unaffected. Stationsbord cannot recover a missing service association
by matching words in descriptions reliably.

The initial v0.9.4 release added expandable general network notices to train
details. In **v0.9.4-r1**, this panel is removed: general notices remain in the
dedicated network view, with incidents separate from works (`type=planned`).
Train details retain explicit train/row/stop messages when supplied. Actual
availability, timing and completeness still depend on the upstream notices.

## GTFS suitability

The FlatTurtle SNCB/NMBS listing publishes static timetable archives (about
29 MiB compressed in the reviewed listing) and realtime `trip-update` and
`alert` endpoints requiring an `x-rt-token`. The advertised endpoints do not
include a vehicle-position feed. Static GTFS supplies trips, stops, stop times
and calendars; it supplies neither a live location nor rolling-stock formation.
The current iRail implementation already uses GTFS for vehicle lookups on days
other than today.

A useful separate addition would be a **planned timetable fallback** when iRail
is unavailable, or retained timetable coverage for dates still present in the
feed. It should be visibly labelled as planned data and never treated as a
source of live delays, tracks, formations or train progress. On the current
256 MiB Fly VM, use a streamed import into an indexed persistent database,
validate calendar/timezone and GTFS times beyond 24:00, and replace feed versions
atomically. Loading the whole expanded archive into the Node request process is
not a suitable default. Route maps would depend on usable shapes in the feed.

GTFS-RT alerts could improve exact trip/route/stop association with entity IDs,
after server-side token configuration, protobuf decoding, feed freshness checks
and joining the feed to its matching static version. A trip update is not a GPS
fix. Neither integration is added speculatively to this release; the implemented
features use the existing iRail proxy and rate-limited shared cache.
